Binary search

If the data is sorted, you do not need to look at every item. Check the middle: if it is your target, you are done; if the target is bigger, discard the left half; otherwise discard the right half. The range halves each step, so the time is O(log n). For a million items, that is about 20 steps.

A sort is stable if equal items keep their original relative order. Python's built-in sorted() and list.sort() use Timsort, which is O(n log n) and stable.

Write merge_sort(arr) that returns a new sorted list. Idea: split in half, sort each half recursively, then merge the two sorted halves.

[[py:merge_sort]]

The base case is a list of 0 or 1 items, which is already sorted. The merge step walks two pointers, always taking the smaller front item; <= (not <) keeps equal items in their original order, making it stable. There are log n levels of splitting, and each level does O(n) merging work, so O(n log n) overall, with O(n) extra space.

Trees

A binary tree node has up to two children. A binary search tree (BST) adds a rule: everything in the left subtree is smaller than the node, and everything in the right subtree is larger. That makes search, insert and delete O(height), which is O(log n) if the tree is balanced but O(n) if it degenerates into a chain.

The four traversals, on a tree with root 8, children 3 and 10:

  • Inorder (left, node, right): gives a BST's values in sorted order.
  • Preorder (node, left, right): useful for copying a tree.
  • Postorder (left, right, node): useful for deleting a tree.
  • Level order (breadth-first): one level at a time, using a queue.

Write a TreeNode class, then:

  1. bst_insert(root, val), returning the root
  2. inorder(root), returning a list
  3. height(root), where an empty tree has height 0
  4. level_order(root), returning a list of levels

Insert 8, 3, 10, 1, 6, 14 and check that inorder gives [1, 3, 6, 8, 10, 14], height is 3, and level order is [[8], [3, 10], [1, 6, 14]].

[[py:tree]]

Insert, inorder and height are naturally recursive: solve for the left and right subtrees, then combine. Level order is not recursive. It uses a deque as a queue and processes exactly len(queue) nodes per level, which is what separates the levels. All four are O(n) except insert, which is O(height).

 Merge sort always takes O(n log n), is stable, and needs O(n) extra space. Quicksort is usually faster in practice and sorts in place, but its worst case is O(n²) (for example, an already sorted array with a bad pivot choice) and it is not stable. Insertion sort, which is close to O(n) on nearly sorted data. In practice, Python's Timsort already exploits that. Inserting sorted data creates a chain, so operations take O(n). Self-balancing trees such as AVL or red-black trees rotate nodes to keep the height around O(log n). Depth-first search goes as deep as possible before backtracking, using a stack or recursion. Breadth-first search explores level by level, using a queue, and finds the shortest path in an unweighted graph. The values in sorted ascending order. A complete binary tree in which every parent is smaller than (min-heap) or larger than (max-heap) its children. The smallest or largest element is always at the root, and push and pop are O(log n). Design these classes, then use them:

  • An abstract base class Account with an owner and a balance, deposit(amount) (reject amounts that are not positive), withdraw(amount), and a describe() method.
  • withdraw must reject a request that goes beyond the balance plus the account's overdraft limit. Each account type decides its own limit through an abstract method.
  • SavingsAccount allows no overdraft. CurrentAccount allows 1000, and its describe() adds a note to the parent's text.
  • A class variable bank_name, and a read-only balance property.

Then create one of each, loop over both calling describe(), and check that withdrawing 600 from a Savings account with 500 fails.

[[py:oop_bank]]
  • Abstract class: Account inherits from ABC and has an @abstractmethod, so Account("x") raises TypeError. Subclasses must implement overdraft_limit.
  • Encapsulation: _balance is marked internal by the underscore, and outside code reads it through the balance property. Python does not enforce privacy, but the convention is universal.
  • Polymorphism: withdraw is written once, yet behaves differently per account type because it calls self.overdraft_limit().
  • Overriding: both subclasses replace overdraft_limit, and CurrentAccount.describe reuses the parent's version through super().
  • Class vs instance variables: bank_name belongs to the class and is shared. owner and _balance belong to each object.
