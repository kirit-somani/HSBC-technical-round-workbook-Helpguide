The routine to use on every coding problem

  1. Restate the problem in your own words.
  2. Clarify the inputs and edge cases: can the input be empty? Negative? Very large? Duplicates? Sorted?
  3. Give an example and say what the answer should be.
  4. Brute force first. Say the approach and its complexity, even if slow. Then say how you would improve it.
  5. Code it in small, clearly named steps, talking as you write.
  6. Test by hand on your example plus one edge case. Run the code if the editor allows it.
  7. State time and space complexity, and mention what you would do with more time.

[[py:mock_first_unique]]

Brute force: for each character, scan the whole string to count it. O(n²). Better: count every character once with a Counter, then walk the string in the original order and return the first index whose count is 1. Time O(n), space O(1), because the alphabet is a fixed size (or O(k) for k distinct characters). The second pass over the original string, not over the counter, is what guarantees "first".

Accumulate with a defaultdict(int), so a missing account starts at 0. For the ordering, sort by a tuple key: -total puts the biggest first, and the account id breaks ties alphabetically. A set is the natural tool: add on login, and remove on logout. discard (not remove) is the detail that handles the "logout without login" edge case, because remove would raise a KeyError. Time O(n + m log m) including the final sort, space O(m). A good follow-up to discuss: what if the same user can log in twice on different devices? Then you would count sessions per user with a dictionary instead of a set.

Explaining your projects

Interviewers pick a project from your resume and dig in. You can be sure they will ask about at least one. Prepare each project using the same six parts.

Write your answer to "Tell me about your project", using these parts, in order:

  1. What it is and who it is for (one sentence)
  2. The problem it solves
  3. Your role (what you built, not "we")
  4. The tech stack and why you chose it
  5. One hard challenge and how you solved it
  6. The result and what you would improve

Then list five follow-up questions an interviewer could ask about it (database design? how did you test it? what if 10,000 users use it at once?) and prepare a one-line answer to each.

A filled-in example of the shape, for a made-up project:

"I built a student attendance tracker for my department. Teachers were marking attendance on paper, which took ten minutes per class and caused errors in the monthly reports. I was the main developer on a team of three, and I built the backend and the database. I used Python with Flask and SQLite, because it is simple to set up and we had under a thousand students. The hardest part was that two teachers sometimes marked the same class at once and overwrote each other, so I added a unique constraint on class and date and handled the error by asking the second teacher to review. It cut the reporting time from hours to seconds. If I extended it, I would move to PostgreSQL and add login roles, since anyone can currently edit anything."

Why this works: it is specific (numbers, names of tools), it says "I", it shows a real problem, and it ends with honest improvements. Prepare the follow-ups too. For this example: "Why SQLite?", "What is your table design?", "How did you test it?", "What happens when 5,000 users log in?"

If a project is weak or a team effort, still own your part in detail. Never claim technology you cannot explain. If you say "REST API", be ready to explain what that is.

Tell me about yourself

Use the present, past, future structure. Write it, read it aloud with a timer, and cut it until it is 60 seconds.

  • Present (15 sec): who you are now. "I'm a final-year B.Tech student in [branch] at [college]."
  • Past (30 sec): two or three things that built your skills. A project, an internship, a competition, a subject you love. "I built [project], where I learned [skill]. I also [achievement]."
  • Future (15 sec): why this role. "I'm excited about this role because [reason connected to the job], and I'd like to grow in [area]."

Do not read out your resume line by line, and do not go back to school days. Finish with a sentence that links to the role, so the interviewer knows where to ask next.

For "tell me about a time when...", answer in four parts: Situation (the context, briefly), Task (what you were responsible for), Action (what you did, the longest part), Result (what happened, with a number if possible, and what you learned).

Write two real stories in STAR format, one about teamwork and one about a mistake or failure. Each should be about 90 seconds spoken. Many questions can be answered by adjusting one of these two stories.

Shape of a good failure story:

Situation: "In our third-year project, I owned the database part."

Task: "I had to finish it a week before the demo."

Action: "I skipped testing with real data, and two days before the demo the app crashed on long names. I told my team immediately instead of hiding it, stayed late to fix it, and wrote tests for the edge cases."

Result: "We demoed on time, and now I test with realistic data from day one. It taught me to raise problems early."

The pattern to copy: a real (not fake-perfect) mistake, your own action, and a concrete lesson that changed your behaviour.
