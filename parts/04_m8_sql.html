Ideas to know before you write queries

Logical order of execution. You write SELECT first, but the database evaluates a query in this order: FROM and JOIN, then WHERE, then GROUP BY, then HAVING, then SELECT, then ORDER BY, then LIMIT. That explains why WHERE cannot use an aggregate like COUNT(*) (groups do not exist yet), while HAVING can.

JoinReturns
INNER JOINOnly rows that match on both sides
LEFT JOINAll rows from the left table, and matches from the right (NULL where there is none)
RIGHT JOINThe mirror image of LEFT JOIN
FULL OUTER JOINAll rows from both sides, matched where possible
Self joinA table joined to itself under two aliases, such as employee and manager

salary = NULL is never true. Use IS NULL or IS NOT NULL. Also, COUNT(*) counts rows, while COUNT(column) skips NULLs. That difference matters in exercise 8.

Find every salary that is shared by more than one employee, and how many employees share it.

Expected: 50000 -> 2,  60000 -> 2
[[sql:q_dup_salary]]

Group by the column that may repeat, then keep only groups with more than one row. HAVING filters after grouping. WHERE would run before the groups exist. This pattern also finds duplicate emails, duplicate account numbers, and so on.

Show each employee who earns more than their own manager, with both salaries.

Expected: Meera 95000, manager Asha 90000
[[sql:q_manager]]

This is a self join: the same table appears twice under the aliases e (employee) and m (manager), matched by e.manager_id = m.id. Employees with no manager drop out of the inner join, which is right here.

Find customers with no rows in orders.

Expected: Bhavna
[[sql:q_never_ordered]]

A LEFT JOIN keeps every customer. Customers with no matching order get NULL in the order columns, so filtering on o.id IS NULL keeps exactly those customers. The alternatives are NOT EXISTS (...) and NOT IN (SELECT customer_id FROM orders). Be careful with NOT IN: if the subquery can return a NULL, the whole condition returns nothing.

List all four departments with their headcount and total salary, largest payroll first. Legal has nobody, and should still appear with zeros.

Expected:
Engineering  3  255000
Operations   3  145000
Finance      2  120000
Legal        0  0
[[sql:q_dept_left]]

Two details make this work. Use LEFT JOIN from departments, so Legal is not dropped. And use COUNT(e.id), not COUNT(*): Legal's single joined row has a NULL employee id, so COUNT(e.id) correctly gives 0, while COUNT(*) would say 1. COALESCE turns the NULL sum into 0.

[[sql:q_window_rank]]

PARTITION BY restarts the ranking for each department, and ORDER BY sets the ranking order. In Operations, salaries 50000, 50000, 45000 give:

ROW_NUMBER()1, 2, 3Always unique, ties broken arbitrarily

 DELETE removes selected rows (it can use WHERE, fires triggers, and can be rolled back). TRUNCATE removes all rows quickly and resets the table, with no WHERE. DROP removes the whole table, including its structure. WHERE filters individual rows before grouping. HAVING filters groups after GROUP BY and can use aggregate functions like COUNT and SUM. INNER JOIN keeps only rows with a match on both sides. LEFT JOIN keeps every row from the left table and fills the right side with NULL where nothing matches. UNION combines two result sets and removes duplicates, which costs a sort or hash. UNION ALL keeps duplicates and is faster. Use UNION ALL when duplicates are impossible or acceptable. A primary key uniquely identifies each row, cannot be NULL, and a table has only one. A unique key also enforces uniqueness, but a table can have many of them, and (depending on the database) they may allow a NULL. An index is a separate structure (usually a B-tree) that lets the database find rows without scanning the whole table, turning an O(n) scan into roughly O(log n). The cost is extra storage and slower inserts, updates and deletes, because the index must be kept in sync. Both can combine data from several tables. Joins are usually clearer and often faster for combining columns. Subqueries read naturally for "compare with an aggregate" or "exists or not" questions. Modern optimizers often turn one into the other. A saved query that behaves like a virtual table. It can simplify complex queries and restrict which columns a user sees, and it stores no data itself (unless it is materialized). COUNT(*) counts all rows. COUNT(column) counts rows where that column is not NULL. COUNT(DISTINCT column) counts the different non-NULL values.
