Normalization

Normalization organizes tables to remove redundancy, so a fact is stored in exactly one place. It prevents three problems: update anomalies (change a value in some rows but not others), insert anomalies (cannot add a fact without unrelated data) and delete anomalies (deleting a row loses unrelated facts).

  • 1NF: every cell holds a single, atomic value, and there are no repeating groups.
  • 2NF: 1NF, plus every non-key column depends on the whole composite key, not just part of it (no partial dependency).
  • 3NF: 2NF, plus non-key columns depend only on the key, not on other non-key columns (no transitive dependency). A common phrase: "every non-key attribute depends on the key, the whole key, and nothing but the key."
  • BCNF: a stricter 3NF, where every determinant is a candidate key.

This table stores course enrollments. The primary key is (student_id, course_id). Assume each course has one instructor, and each instructor has one office.

student_id | course_id | student_name | course_name | instructor | instructor_office
1          | C1        | Asha         | Databases   | Dr Rao     | Room 201
1          | C2        | Asha         | Networks    | Dr Iyer    | Room 305
2          | C1        | Ravi         | Databases   | Dr Rao     | Room 201

Find the partial and transitive dependencies, then split the table.

Partial dependencies (violate 2NF): student_name depends only on student_id, and course_name depends only on course_id. Asha's name is stored twice, so renaming her means editing several rows.

Transitive dependency (violates 3NF): course_id → instructor → instructor_office. The office depends on the instructor, who depends on the course, so the office is repeated for every enrollment in Dr Rao's course.

Result in 3NF:

Student(student_id PK, student_name)
Instructor(instructor_id PK, instructor_name, office)
Course(course_id PK, course_name, instructor_id FK)
Enrollment(student_id FK, course_id FK, PRIMARY KEY (student_id, course_id))

Each fact now lives in one place. Trade-off to mention: more tables means more joins when reading, so read-heavy systems sometimes denormalize on purpose for speed.

Transactions and ACID

A transaction is a group of operations that must succeed or fail as one unit. The classic example is a transfer: money must not leave one account unless it arrives in the other.

Concurrency problems and isolation levels

  • Dirty read: reading data another transaction has changed but not yet committed.
  • Non-repeatable read: reading the same row twice in one transaction and getting different values, because someone committed a change in between.
  • Phantom read: running the same query twice and getting extra rows, because someone inserted matching rows in between.

Which level prevents which problem, as defined by the SQL standard (real databases vary slightly):

Higher isolation is safer but slower, because transactions wait for each other more.

Indexes

[[sql:index_example]]

An index is like the index at the back of a book: instead of reading every page, you look up the term and jump to the page. Most databases use a B+ tree, keeping lookups at O(log n). Index the columns you filter, join or sort on often. Do not index everything: each index uses space and slows down writes. A clustered index decides how the rows are physically stored (one per table, often the primary key), while a non-clustered index is a separate structure that points to the rows.

A DBMS is any software that stores and manages data. An RDBMS stores data in related tables (rows and columns) with keys and relationships, and uses SQL. Examples are MySQL, PostgreSQL, Oracle and SQL Server. We normalize to remove redundancy and avoid update, insert and delete anomalies. We denormalize when reads must be fast and joins are too expensive, accepting duplicated data and more careful updates. DDL defines structure (CREATE, ALTER, DROP). DML manipulates data (INSERT, UPDATE, DELETE, SELECT). DCL controls access (GRANT, REVOKE). TCL controls transactions (COMMIT, ROLLBACK, SAVEPOINT). SQL databases have fixed schemas, tables and strong ACID guarantees, which suits banking and other structured data. NoSQL databases (document, key-value, column, graph) offer flexible schemas and easier horizontal scaling, often trading away some consistency guarantees. An Entity-Relationship diagram is a picture of the entities in a system (like Customer, Account), their attributes, and the relationships between them (one-to-one, one-to-many, many-to-many). It is used to design tables before writing them.

An operating system manages hardware for programs: it shares the CPU between processes, hands out memory, and gives programs a clean way to use disks and networks. Programs ask the kernel for these services through system calls. The CPU runs in user mode for applications and kernel mode for trusted OS code, so one buggy program cannot damage the whole machine.

A context switch is when the CPU saves one process's state and loads another's. It is pure overhead, since no useful work happens during it.

CPU scheduling

  • FCFS (first come, first served): simple, but a long job at the front delays everyone (the convoy effect).
  • SJF (shortest job first): gives the lowest average waiting time, but needs to know burst times and can starve long jobs.
  • Round robin: each process gets a fixed time quantum in turn. Fair and good for responsiveness. Too small a quantum wastes time on switches.
  • Priority: the highest priority runs first. Low-priority processes can starve, which is fixed by aging (slowly raising the priority of waiting processes).

Formulas: turnaround time = completion time − arrival time, and waiting time = turnaround time − burst time.

Three processes all arrive at time 0: P1 needs 5 units of CPU (its burst time), P2 needs 3, and P3 needs 8. Calculate the average waiting time for:

  1. FCFS, in the order P1, P2, P3
  2. SJF (non-preemptive)
  3. Round robin with a time quantum of 4

For round robin, P1 runs 0 to 4 and has 1 unit left, so it rejoins the queue. P2 finishes at 7. P3 runs 7 to 11 and has 4 left. P1 finishes at 12, then P3 finishes at 16. Since everyone arrives at 0, waiting = completion − burst.

What to conclude: SJF gave the lowest average waiting time, which is a known result. Round robin had the highest average here, but it gives every process the CPU early, so it has the best response time.

Deadlock

A deadlock is a set of processes that each wait for a resource another holds, so none can ever proceed. Example: thread A holds lock 1 and wants lock 2, while thread B holds lock 2 and wants lock 1. Deadlock needs all four conditions (the Coffman conditions):

  1. Mutual exclusion: a resource can be used by only one process at a time.
  2. Hold and wait: a process holds one resource while waiting for another.
  3. No preemption: a resource cannot be forcibly taken away.
  4. Circular wait: a cycle of processes, each waiting for the next.

Prevention means breaking one condition, for example by making every thread acquire locks in the same fixed order (breaks circular wait). Avoidance uses the Banker's algorithm to grant a request only if the system stays in a safe state. Detection and recovery finds the cycle and kills or rolls back a process.

Synchronization

A race condition happens when the result depends on the timing of threads touching shared data. The code that touches shared data is a critical section, and it must run one thread at a time. A mutex is the lock that provides this.

Memory management

  • Paging splits memory into fixed-size pages (in the process) and frames (in RAM). There is no external fragmentation, but the last page of a process can waste space (internal fragmentation).
  • Segmentation splits memory into variable-size logical pieces (code, stack, heap). It matches how programmers think but suffers from external fragmentation.
  • Virtual memory lets a process use more memory than physically exists, by keeping only the needed pages in RAM and the rest on disk.
  • A page fault happens when a needed page is not in RAM, so the OS loads it from disk (slow). Thrashing is when the system spends more time swapping pages than doing work, because too many processes compete for too little RAM.

A process uses 3 frames of memory and requests these pages in order: 7, 0, 1, 2, 0, 3, 0, 4. Count the page faults under:

  1. FIFO: replace the page that has been in memory the longest
  2. LRU: replace the page that was used least recently

The difference appears when page 3 arrives: FIFO throws out page 0 because it is the oldest, even though it was used a moment ago, and then faults on 0 again at the next request. LRU keeps page 0 and evicts page 1 instead. LRU works well because recently used pages are likely to be used again (locality). Mention Belady's anomaly: with FIFO, giving a process more frames can sometimes cause more faults. LRU does not have this problem.

 A process is a running program with its own address space. A thread is a lighter unit of execution inside a process that shares the process's memory with its sibling threads. Threads are cheaper to create and switch, but sharing memory requires careful synchronization. Saving the state of the running process (registers, program counter) and loading the state of another. No useful work happens during the switch, and the CPU caches also become less useful. Too many switches hurt performance. Mutual exclusion, hold and wait, no preemption, and circular wait. All four must hold together. Breaking any one prevents deadlock. In a deadlock, a group of processes wait on each other forever. In starvation, one process waits indefinitely because others keep getting priority, but the system as a whole keeps moving. Aging is a common fix for starvation. A mutex is a lock owned by one thread at a time, used for mutual exclusion. A semaphore is a counter allowing up to N holders and can also be used for signalling between threads. A binary semaphore looks like a mutex but has no ownership. Paging uses fixed-size blocks, avoids external fragmentation, and is invisible to the programmer. Segmentation uses variable-size blocks that match logical units like code and stack, and can suffer external fragmentation.
